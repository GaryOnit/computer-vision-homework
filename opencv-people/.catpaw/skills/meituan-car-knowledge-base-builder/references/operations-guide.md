# 知识库运营操作手册

> 本文件对应 SKILL.md 阶段 6A～6G 的详细操作步骤。

## §1 规则体系初始化（rule-init / 6A）

### 1.1 标准规则章节定义

执行 `rule-init` 时，AGENTS.md 需要包含以下标准章节：

| 章节 | 必须 | 说明 |
|------|------|------|
| 信息可信度分级 | ✅ | L1/L2/L3 对应来源类型 |
| 知识库路径 | ✅ | P0/P1/P2/P3 分级路径列表 |
| 已知坑速查 | ✅ | 5-8 条高频坑（从 implicit-knowledge.md 摘取）|
| 编码约束 | ✅ | 仓库特有规范（继承关系、接口约定等）|
| 环境依赖 | ✅ | Node 版本、外部依赖等 |
| 模块知识库目录总览 | ✅（有子模块时）| 模块→文档路径映射 |

### 1.2 智能合并规则

```
对比现有 AGENTS.md 与标准章节：
  章节不存在 → 新增（追加）
  章节存在且内容相同 → 跳过
  章节存在但内容不同 → 展示 diff，等待用户选择（保留本地 / 采用标准 / 手动合并）
  仓库独有章节（标准中没有）→ 保留，输出到质量检查报告
```

### 1.3 质量检查报告格式

```markdown
## 仓库独有规则质量检查报告

### ✅ 无问题的独有规则
- `编码约束 > ViewModel 统一继承 BaseViewModel` — 可执行，语义清晰

### ⚠️ 建议优化的独有规则
| 编号 | 规则内容 | 问题 | 建议 |
|------|---------|------|------|
| U-1 | "注意代码质量" | 无法执行（原则类）| 改为具体约束，如"函数体不超过50行" |
| U-2 | "合理处理错误" | 含模糊词 | 改为"catch 块 MUST 记录日志并上报 Raptor" |

输入 `apply U-1,U-2` 应用建议，或 `skip` 跳过。
```

## §2 踩坑自动沉淀（6B）

### 2.1 触发信号识别规则

自动识别以下模式（优先级从高到低）：

| 信号类型 | 示例 | 分类 |
|---------|------|------|
| 显式纠偏 | "不对"、"你搞错了"、"应该是 X 不是 Y" | 知识过时或错误 |
| 补充新知识 | "你不知道的是…"、"这个有个特殊规则" | 知识缺失 |
| AI 猜测失准 | AI 说"我猜是"后结果错误 | 知识缺失 |
| 隐式纠偏 | 用户第 3 次说同一个需求，前两次 AI 都跑偏 | AI 执行规则缺失 |
| 主动复盘 | "帮我复盘"、"这次哪里出了问题" | 综合 |

### 2.2 沉淀文件格式

路径：`docs/experience/<分类>/<YYYY-MM-DD>-<简短标题>.md`

分类目录：
- `missing-knowledge/` — 知识缺失（AI 不知道某个事实）
- `stale-knowledge/` — 知识过时（AI 知道但信息已过期）
- `missing-rules/` — 执行规则缺失（AI 应遵守但没遵守某约束）
- `other/` — 其他

```markdown
---
topic: <一句话描述这个坑>
keywords: [相关术语, 文件名, 类名]
triggers: [什么场景会踩这个坑]
confidence: L3
source: 对话沉淀（<YYYY-MM-DD> 会话）
updated: <YYYY-MM-DD>
---

# <坑的标题>

## 根因
<AI 为什么出错：缺少了什么知识/规则>

## 正确做法
<应该怎么做>

## 错误示例
```code
// ❌ AI 的错误输出
```

## 正确示例
```code
// ✅ 正确的做法
```

## 关联文件
- `<文件路径>` — <说明>
```

### 2.3 同步 implicit-knowledge.md

当踩坑属于"知识缺失"且涉及具体文件/类的特殊行为时，同步追加到 `docs/implicit-knowledge.md` 的「已知特殊设计」表格。

## §3 知识库召回率统计（6C）

### 3.1 日志文件格式

日志路径：`agent_log/doc_log/<mis>.json`

```json
{
  "logs": [
    {
      "date": "2026-06-01",
      "session_id": "abc123",
      "docs_loaded": ["docs/service-api-index.md", "docs/quick-lookup.md"],
      "docs_referenced": ["docs/service-api-index.md"]
    }
  ]
}
```

### 3.2 召回率报告输出格式

```markdown
## 知识库召回率报告（统计区间：<日期范围>）

### 高频文档 TOP5
| 文档 | 被引用次数 | 占比 |
|------|-----------|------|
| docs/quick-lookup.md | 23 | 38% |
| docs/service-api-index.md | 18 | 30% |
| ... | | |

### 零引用文档（⚠️ 写了但从未被 AI 用到）
| 文档 | 最后更新 | 可能原因 | 建议 |
|------|---------|---------|------|
| docs/terminology.md | 2026-01-15 | keywords 不匹配触发词 | 补充业务场景触发词 |
| docs/api-protocol.md | 2026-02-01 | frontmatter 缺少 triggers | 补充 triggers 字段 |

输入 `fix-recall <文件名>` 让 AI 帮你优化 frontmatter。
```

### 3.3 frontmatter 优化建议

对零引用文档，执行以下分析：
1. 检查 `keywords` 是否包含用户常说的业务词（如"搜索"而非"Search"）
2. 检查 `triggers` 是否覆盖真实使用场景
3. 检查 `topic` 是否足够具体（"接口文档" → "XXX 模块接口参数说明"）

## §4 增量更新检查清单（6D）

新增文件/模块后必须依次更新：

```bash
# 1. 扫描新文件
find src/ -newer docs/README.md -name "*.java" | head -20

# 2. 读取新增文件（分批，每批 3-5 个）
# 参考 workflow-detail.md §4 批量读取策略

# 3. 更新索引（按顺序，不要跳过）
# service-api-index.md → 追加新 Service 行
# file-index.md        → 追加新文件路径
# quick-lookup.md      → 追加新业务场景映射
# docs/README.md       → ⚠️ 更新目录 + 更新文件数量（最常遗漏！）

# 4. 更新可信度
# 每个新增文档的 updated 字段改为今天日期
```

## §5 规则质量检查全量定义（rule-check / 6E）

| 编号 | 优先级 | 检查内容 | 判断标准 |
|------|--------|---------|---------|
| R1 | 🔴高 | 原则类规则 | 能否转化为 yes/no 可判断的操作？不能则为原则类 |
| R2 | 🔴高 | 触发条件不合格 | 是否有具体触发词/短语？ |
| R3 | 🟡中 | 强制标签滥用 | 主文件 MUST/NEVER 比例 >60%，子文档 >30% |
| R4 | 🟡中 | 语义重复 | 同一约束在多处表述是否语义等价？ |
| R5 | 🟠低 | 示例与项目不符 | 示例中的类名/路径在仓库中是否存在？ |
| R6 | 🟠低 | 信息密度不足 | 规则是否只有标题无内容？ |
| R7 | 🟡中 | 触发场景合并过多 | 单条规则是否涵盖 >3 个差异场景？ |
| R8 | 🔴高 | 执行项含模糊词 | 包含"合理"/"适当"/"注意"/"尽量"等 |
| R9 | 🟡中 | 主/子文档分类错误 | 超过 30 行的内容是否在主文件而非 references/ |
| R10 | 🔴高 | 按需指针失效 | 引用的文件路径是否实际存在？ |
| R11 | 🟡中 | 子文档格式不符规 | 子文档是否有 frontmatter？ |
| R12 | 🟡中 | 规则标题为触发条件 | 标题写成"当...时"格式而非动作描述 |
| R13 | 🟡中 | 全局约束格式违规 | 全局约束是否独立成节而非分散在各处 |
| R14 | 🔴高 | 主子分类整体审查 | 主文件是否超过 500 行（拆到 references/）|
| R15 | 🟡中 | 可合并规则识别 | 是否存在可以合并的相似规则 |
| R16 | 🟡中 | 规则存储分类不符 | 规则类型与所在目录/文件是否匹配 |

## §6 知识库文档质量检查全量定义（doc-check / 6F）

### 文件级检查（D1～D11）

| 编号 | 优先级 | 检查内容 | 判断标准 |
|------|--------|---------|---------|
| D1 | 🔴高 | frontmatter 存在性 | 文件第一行是否为 `---` |
| D2 | 🔴高 | frontmatter 必填字段 | 是否包含 topic/keywords/triggers/confidence/source/updated |
| D3 | 🔴高 | confidence 字段有效 | 值是否为 L1/L2/L3 之一 |
| D4 | 🟡中 | keywords 写法 | 是否至少有 3 个关键词，是否含中英文同义词 |
| D5 | 🟡中 | 结论未前置 | 核心结论是否在文件前 1/3 出现 |
| D6 | 🟡中 | 叙述内容未标注 | 长背景段落是否有"<!-- AI 可跳过 -->"注释 |
| D7 | 🟡中 | 多主题检测 | 语义分析：文件是否同时覆盖 >2 个不相关概念 |
| D8 | 🔴高 | 代码一致性 | 文档中的方法签名/参数是否与代码文件一致 |
| D9 | 🟠低 | 可信度标注 | 每段来自不同来源的内容是否标注了 confidence |
| D10 | 🟠低 | 代码细节内联 | 单次内联代码块是否超过 5 行（建议改路径索引）|
| D11 | 🟡中 | 「待确认」项过期 | `[待确认]` 标注是否超过 30 天未处理 |

### 目录级检查（D12～D16）

| 编号 | 优先级 | 检查内容 | 判断标准 |
|------|--------|---------|---------|
| D12 | 🔴高 | docs/ 目录存在 | 仓库根目录是否有 docs/ 目录 |
| D13 | 🟡中 | 子目录语义化 | 目录名是否语义清晰（避免 v1/、temp/、misc/）|
| D14 | 🟡中 | 避免缩写目录名 | 是否使用了难以理解的缩写（如 kb/ 而非 knowledge-base/）|
| D15 | 🟡中 | 层级不宜过深 | 嵌套是否超过 3 层 |
| D16 | 🟠低 | 通用占位文件名 | 文件名是否过于通用（如 info.md、notes.md、temp.md）|

## §7 代码目录结构检查全量定义（struct-check / 6G）

| 编号 | 优先级 | 检查内容 | shell 检测命令（参考线索，非最终结论）|
|------|--------|---------|--------------------------------------|
| S1 | 🔴高 | AGENTS.md 缺失 | `ls AGENTS.md 2>/dev/null` |
| S2 | 🟡中 | 根目录散落文件过多 | `find . -maxdepth 1 -name "*.md" -o -name "*.json" -o -name "*.yaml" \| wc -l` |
| S3 | 🟡中 | 目录名使用纯动词 | 语义分析识别 handle/、process/、execute/ 等 |
| S4 | 🟡中 | 空目录 | `find src/ -type d -empty` |
| S5 | 🟡中 | 代码模块用纯技术分层命名 | 是否存在 controller/、service/、repository/ 等纯技术分层（无业务语义）|
| S6 | 🟡中 | 工具类混入业务模块 | `find src/ -path "*/modules/*/utils" -type d` |
| S7 | 🟠低 | 模块目录名使用缩写 | 语义分析识别 mgr/、svc/、repo/ 等 |
| S8 | 🔴高 | 文件名与类名不一致 | 对每个 .java 文件，检查文件名是否与 `public class/interface` 声明一致 |
| S9 | 🟠低 | 业务模块缺少测试镜像目录 | `src/main/java/*/modules` 是否在 `src/test/java` 有对应目录 |

**执行策略**：优先使用语义分析（S3/S5/S7），shell 命令仅作为候选线索加速器，不直接作为最终结论。

## §8 大象消息推送（通用能力）

各运营场景完成关键操作后可推送大象消息：

```bash
# 安装 dx-push（首次）
npm install -g dx-push --registry=http://r.npm.sankuai.com

# 推送消息
dx-push send --to <mis> --content "知识库运营完成：<场景名称>\n- 更新文件：<N> 个\n- 新增踩坑记录：<N> 条"
```

失败时不影响主流程，静默跳过。
